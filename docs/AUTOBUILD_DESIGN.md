# StartupOS AutoBuild 설계 v1

상태: 설계안. AutoBuild 실행기는 아직 구현하지 않았다. 기존 로그인/워크스페이스 수정과 구분한다.

## 1. 제품 목표

사용자는 서비스 기획과 제약, 원하는 품질, 허용 예산을 입력하고 AutoBuild를 한 번 시작한다. 서버는 요구사항을 분해하고 실제 코드를 수정하며, 검증에서 발견한 문제로 다음 지시를 작성한다. 필수 기능과 사용자 여정이 검증될 때까지 필요한 부분을 반복한다. 탭을 닫거나 기기를 바꿔도 동일 runId로 이어진다.

N은 항상 소비해야 하는 횟수가 아니라 전체 구현·검증 시도의 상한이다. 품질 기준을 일찍 만족하면 종료한다. 한 번의 시도는 작업 지시 → 코드 변경 → 실행 검증 → 채택/수정/상위 재설계 판정이다. 한 시도 안의 모델 호출·도구 호출은 별도로 비용과 횟수를 기록한다.

## 2. 계층과 책임

| 계층 | 책임 | 반복 조건 |
| --- | --- | --- |
| L0 제품 계약 | 사용자 목표, 필수 요구사항, 제약, 허용 예산, 성공 기준 확정 | 사용자 변경 또는 명시적 범위 변경 |
| L1 사용자 여정 | 로그인부터 실제 결과 저장·재접속까지 통합 시나리오 설계·검증 | 기능을 합쳤을 때 여정 실패, UI/UX 품질 미달 |
| L2 기능 작업 | 인증, 프로젝트 관리, 촬영, 분석, 저장 등 기능별 의존성·인터페이스 관리 | 기능 검증 실패, API/데이터 계약 불일치 |
| L3 구현 시도 | 제한된 파일 범위에서 코드 수정, 테스트 실행, 원인 수정 | 재현 가능한 실패가 남아 있음 |

기능 안에서 3회 의미 있는 수정을 해도 같은 문제가 남으면 L2가 접근법을 바꾼다. 기능 간 결합 문제는 L1로, 목표/제약 간 충돌은 L0로 올린다. 재설계가 요구사항 삭제나 성공 기준 완화로 이어지면 새 계약 버전과 사용자 판단이 필요하다.

논리적 역할과 모델 프로세스 수는 분리한다. 초기 버전은 실행 관리자 1개, 기획·기술 총괄, 구현 작업자, 독립 평가자로 시작한다. 모든 단계에서 여러 고가 모델을 동시에 호출하지 않는다.

## 3. 실행 구조

- AutoBuild Controller: 코드로 작성한 상태 전이, 예산 예약, 재시도·중단·승격 정책. LLM 점수만으로 완료를 결정하지 않는다.
- Planner: 버전이 고정된 acceptance contract와 기능 DAG 생성.
- Builder: 격리된 체크아웃에서 파일 읽기/수정, 의존성 설치, 빌드·테스트 도구 사용.
- Verifier: 원래 요구사항과 테스트·실행 증거를 보고 성공/실패 판정. Builder의 완료 주장으로 판정하지 않는다.
- UX Reviewer: 실제 화면과 사용자 행동 시나리오를 검토해 재현 경로와 화면 위치를 포함한 수정 지시 생성.
- Release Manager: 검증된 정확한 커밋을 프리뷰로 배포하고 배포된 버전에서 주요 여정을 재확인.

초기 동시 작업 수는 2개를 권장한다. 공통 API/스키마 계약이 먼저 확정된 독립 기능만 분리된 브랜치/워크스페이스에서 병렬 실행한다. 통합 브랜치에는 한 번에 하나씩 반영하고 영향을 받은 여정을 재검증한다.

## 4. 품질 계약과 증거

시작 시 다음 항목을 requirement ID와 acceptance test ID로 고정한다.

- 필수 사용자 기능과 제외 범위
- 정상 흐름, 오류·취소·권한 거절, 새로고침, 재접속, 다른 계정 접근
- 화면 폭과 입력 장치 등 테스트 환경
- 성능 목표와 측정 방법
- 사용자에게 필요한 결과와 저장·조회 방식
- 실제 외부 서비스 연동이 필요한 항목
- 코드 수정·프리뷰 배포·운영 배포의 허용 범위

증거 연결은 requirementId → testId → executionId → commitSha/artifactHash → previewDeploymentId이다. 통합 후 코드가 바뀌면 관련 증거를 무효화한다. 최종 완료 판정은 최종 배포 커밋의 증거를 사용한다.

구현 모델은 필수 테스트를 삭제하거나 skip 처리하고, assertion을 완화하거나 요구사항을 지워서 통과시킬 수 없다. 테스트 자체가 잘못됐다고 판단되면 별도 검토 사유와 계약 버전 변경을 남긴다.

로컬 mock, 에뮬레이터, 실제 공급자 API, 실제 휴대폰 확인은 서로 다른 증거 수준으로 표시한다. mock 통과로 실제 로그인·결제·기기 카메라까지 성공했다고 표시하지 않는다.

UX 평가는 명확한 기준표와 화면 증거로 한다. 예: 핵심 CTA 접근성, 다음 행동의 명확성, 오류 복구, 입력 유지, 작은 화면의 잘림, 터치 조작. 점수는 참고값이며 필수 기능 실패를 상쇄할 수 없다.

## 5. 한 번의 반복

1. Controller가 준비된 DAG 노드 중 우선순위가 가장 높은 실패를 고른다.
2. Builder에게 관련 요구사항, 현재 코드 SHA, 재현 경로, 실패 로그/화면, 수정 가능 파일, 금지 사항, 예산을 제공한다.
3. Builder가 실제 패치를 만들고 변경 요약을 반환한다.
4. 테스트 도구가 패치가 적용된 동일 SHA에서 검증한다.
5. 독립 평가자가 요구 충족 여부와 UI/UX를 판정한다.
6. 통과하면 체크포인트를 저장하고 상위 기능/여정을 다시 평가한다.
7. 실패하면 관측된 원인과 다음 수정 지시를 만든다.
8. 반복 실패면 기능 설계/인터페이스/구현 전략을 상위 단계에서 재검토한다.

그동안 다른 독립 기능은 계속 작업할 수 있다. 외부 설정이 막힌 노드 때문에 전체 구현 큐를 멈추지 않으며, 해당 항목이 필수라면 최종 완료 상태는 차단한다.

## 6. 실패 유형별 처리

| 실패 | 처리 |
| --- | --- |
| 구문·타입·빌드 오류 | 해당 변경에 대한 로컬 수리 |
| 테스트 assertion 실패 | 재현 케이스를 유지한 채 원인 수정 |
| 기능 간 통합 실패 | L1/L2에서 데이터·API 계약 재검토 |
| 같은 오류 반복, 실질 개선 없음 | 모델/접근법 변경, 상위 재설계, 최선 버전 보존 |
| 일시적 429/네트워크 오류 | Retry-After/백오프; 의미 있는 구현 회차와 분리 기록 |
| Firebase/배포 서비스의 권한·설정 부재 | BLOCKED_EXTERNAL; 필요한 설정과 검증할 항목만 표시 |
| 예산·시간·전체 회차 상한 도달 | 완료로 표시하지 않고 체크포인트와 미충족 요구사항 반환 |
| 사용자 새 지시 | 계약 버전 증가, 영향 노드 재계획, 오래된 결과 적용 방지 |
| 실행기 재시작/중복 메시지 | 저장된 단계에서 재개, 중복 변경/배포를 식별하여 재사용 |

현재 StartupOS의 Firebase 미설정·Vercel 팀 403은 코드 수리 반복으로 해결할 수 있는 실패와 구분해야 한다.

## 7. 종료 조건

COMPLETE 조건:

- 해당 계약의 필수 acceptance test가 모두 통과
- 최종 통합 버전의 주요 사용자 여정 통과
- 차단 수준 버그와 필수 외부 연동 대기 항목이 없음
- 설정한 성능·UX 기준 충족
- 필수 증거 수준 충족
- 최종 커밋·프리뷰·테스트 결과 일치

그 외 상태는 RUNNING, VERIFYING, REPLANNING, PAUSED, BLOCKED_EXTERNAL, NEEDS_DECISION, BUDGET_LIMIT, PLATEAU, FAILED, CANCELED로 구분한다. 예산 소진이나 최대 회차 도달을 성공으로 취급하지 않는다.

“최대한의 품질”은 무한한 개선을 의미하지 않는다. 필수 기준을 만족한 뒤 남은 개선 이득과 추가 비용을 비교한다. 계속할 가치가 낮거나 정체되면 최선 버전과 개선 후보를 반환한다.

추천 초기 정책:

- 전체 최대 50회 구현·검증 시도
- 같은 기능 3회 실패 후 상위 재설계
- 통합 개선 최대 3차
- 동시 Builder 최대 2개
- 실제 금액 상한과 최대 실행 시간은 프로젝트 예산에서 시작 전에 설정
- 비용이 드는 호출 전에 서버에서 동시성까지 고려한 예산 예약
- 핵심 정책은 run 단위로 고정하고 변경 이력 기록

이는 초기 정책 제안이며 실행 시간·성공률·비용의 보증값이 아니다.

## 8. 데이터 모델

기존 owner UID / Venture session ID 아래에 별도 run 데이터를 둔다.

- AutoBuildRun: ownerUid, sessionId, runId, contractVersion, baseCommit, bestCommit, state, limits, reservedCost, settledCost, createdAt, updatedAt
- Requirement: requirementId, parentId, mandatory, acceptanceTestIds, evidenceLevel, status
- TaskNode: taskId, parentId, dependsOn, allowedPaths, attemptCount, status, leaseOwner, leaseExpiry, inputHash
- Attempt: attemptId, taskId, instructionVersion, inputCommit, outputCommit, changedFiles, result, cost
- Verification: testId, executionId, commitSha, environment, providerMode, result, evidenceRefs
- Event: eventId, runId, taskId, type, at, conciseUserMessage
- Artifact: commitSha, archiveRef, screenshots, logs, previewDeploymentId, artifactHash

스크린샷·대형 로그·소스 아카이브는 객체 저장소에 보관하고 문서 DB에는 참조만 저장한다. client가 실행 상태·예산 정산·검증 결과를 임의로 확정하지 못하도록 서버 전용 쓰기 경계를 둔다.

## 9. 실행 내구성과 기술 선택

현재 StartupOS는 정적 UI와 CommonJS Vercel API 함수들로 이루어져 있다. 기존 /api/refine의 코드 제안, /api/build의 조립·검증, /api/publish의 배포를 작업 어댑터로 활용할 수 있다.

실행 관리자는 별도 패키지/서비스로 둔다. Vercel Workflow 같은 지속 실행 엔진에 단계별 작업을 등록하고, 실제 생성 코드의 빌드·테스트는 Vercel Sandbox 등의 격리된 실행 환경에서 수행하는 구성을 권장한다. 기존 프론트 전체를 새 프레임워크로 바꾸는 것을 전제로 하지 않는다. SDK 도입 시 기존 CommonJS 함수와의 빌드·라우팅 호환성을 먼저 작은 실험으로 확인한다.

API는 실행 시작/조회/일시정지/재개/취소/추가 지시만 처리한다. 브라우저는 상태를 구독하며 실행의 주체가 아니다. 각 단계는 커밋/아티팩트와 결과를 저장하고 끝난다. 작업 lease와 재시도 키를 두고, 외부 호출의 타임아웃 이후 성공 여부가 불명확하면 재조회·대사를 우선한다.

현재 Builder는 receipt/skin/travel의 검토된 모듈과 제한된 파일 편집에 기반한다. 범용 AutoBuild에는 새 화면, API, 데이터 모델, 필요한 테스트까지 생성·수정하는 저장소 수준 작업 어댑터를 추가해야 한다. 템플릿 미지원 요구를 완료로 표시하거나 원래 기획에서 제거하지 않는다.

ChatGPT에서 사용하는 연결 도구·계정 권한은 StartupOS 서버로 자동 전달되지 않는다. 실행기에 모델 호출, 저장소 접근, 작업 실행, 프리뷰 배포, 외부 서비스 테스트를 위한 별도 서버 연결이 필요하다. 기존 서버 모델 설정을 활용하고 새로운 공급자 키 도입은 필요할 때만 검토한다.

## 10. 화면 흐름

시작 화면:

- 대상 Venture / 기획 계약
- 빠른 기능 검증 / 출시 후보 품질 모드
- 비용·실행 시간·최대 회차
- 허용된 자동 실행 범위
- AutoBuild 시작

진행 화면:

- 기획 → 사용자 여정 → 기능 → 현재 수정의 작업 트리
- “로그인 후 재접속 테스트에서 세션이 풀려 수정 중”처럼 관측된 작업 상황
- 필수 기준 통과 수 / 전체 수, 미검증·외부 대기 수
- 누적 사용 비용·예약 비용·남은 한도
- 현재 결과와 최선 프리뷰
- 회차별 코드 차이·화면·실패·재검증 결과
- 일시정지 / 재개 / 취소 / 새 지시

사용자의 추가 지시는 현재 run의 새 계약 버전으로 반영한다. 관련 작업만 다시 열고, 이미 검증한 무관한 기능의 결과는 보존한다.

종료 화면은 COMPLETE와 외부 연결 대기를 구분하고, 구현된 범위·실제 검증 범위·남은 일·최선 버전·비용을 함께 보여준다.

## 11. 적용 순서

1. 현재 로그인·워크스페이스의 회귀 검증과 운영 설정을 정리한다.
2. Acceptance Contract, Requirement IDs, 실행 DAG와 run 저장을 구현한다.
3. 기존 코드 수정·빌드·검증을 연결해 기능 하나에서 자동 수리 루프를 완성한다.
4. 사용자 여정 통합 검증과 독립 UX 평가를 추가한다.
5. 예산 예약, 중단·재개, 체크포인트, 정체 감지와 상위 재설계를 추가한다.
6. 저장소 수준 범용 구현 어댑터와 제한된 동시 기능 개발을 확장한다.

첫 시범은 피부 분석 앱의 실제 로그인 → 촬영/선택 → 분석 → 저장 → 재접속 → 다른 계정 접근 차단으로 잡는다. API 설정 부재, 촬영 권한 거절, 작은 화면 CTA, 분석 실패/재시도, 새로고침/기기 전환을 각각 독립 acceptance test로 검증한다.
